# 生活频率 life-frequency

给麦麦一份**持续的小生活**，并按这份生活状态缩放每个会话的**发言频率**。

她睡觉时不回话（连 `@` 也叫不动）、感冒时话少、深夜做题时顾不上闲聊、
攒了「想跟你说的素材」时话又变多。作息活动由 LLM 依人设与近期经历生成，
情绪体力 / 身体 / 日期节日按参考设定推演；**经济**维度读 `budget-pacer` 的
真实月度预算当她的生活费——手头紧时会犹豫、省着花、在家吃泡面，但不主动哭穷。

- 插件 ID：`org.orge-8.life-frequency`
- 宿主：MaiBot `1.2.3 ~ 1.3.2`（上限是**实测过的**范围，不是「永远兼容」的占位）
- SDK：`maibot-plugin-sdk 2.8.0 ~ 2.8.2`
- 依赖：**无**（不联网、不需要额外 Python 包；经济维度可选，未装预算插件会自动降级）

## 安装

1. 把整个 `life-frequency/` 目录放进 MaiBot 的 `plugins/` 下：

   ```
   MaiBot/
   └── plugins/
       └── life-frequency/
           ├── _manifest.json
           ├── plugin.py
           ├── life_config.py        # 配置模型与 WebUI 展示元数据
           ├── life_*.py             # 纯逻辑模块
           └── ...
   ```

   运行时只需要 `.py` + `_manifest.json`（约 **1.0 MB**）。下面这些**不必**放进真机：

   | 可省略 | 理由 |
   |---|---|
   | `tests/` | 开发侧门禁，宿主不加载（约 950 KB） |
   | `collect_diagnostics.py` | 现场诊断工具，按需单独拷（约 240 KB） |
   | `CHANGELOG.md` / `docs/` | 文档，不参与加载 |
   | `check_plugin.py` / `run_gates.py` / `calibrate_curves.py` / `simulate_drift.py` | 开发工具 |

   整目录替换当然也能跑，只是白占体积；`__pycache__/` 一律先删掉再拷贝
   （Windows 上跨机器复制 `.pyc` 会因为解释器版本不同而报错）。

2. **完整重启 MaiBot**（不是热重载）。首次启动时 Runner 会按配置模型生成
   `plugins/life-frequency/config.toml`。
3. 看启动日志有没有 `E_CAPABILITY_DENIED` 或「插件配置版本非法」。
   （`capabilities` 变更**必须**完整重启才重新授权，热重载不生效。）
   升级同理：新增配置字段（如 v1.7.0 的 `[simulation] wake_on_at` / `wake_minutes`）
   由 Runner 按配置模型自动补进 `config.toml` 并取默认值；改这些开关走**配置热重载**，
   但**替换整目录必须完整重启**（辅助模块改动会被 `sys.modules` 缓存住）。
4. 状态文件写在 Runner 授予的数据目录：`data/plugins/org.orge-8.life-frequency/life_state.json`。
   **不要**把它放进插件目录——插件目录可能只读或被清空。

### 建议的第一次运行

先开**演算模式**跑一天，确认倍率走向符合预期，再让它真的写回宿主：

```toml
[simulation]
dry_run = true
```

演算模式下插件照常推进、照常算倍率、照常写日志，只是不调 `frequency.set_adjust`。
用 `/生活 频率` 看拆解即可。

## 它到底怎么影响发言频率

插件只做一件事：往宿主的 `frequency.set_adjust` 写一个**倍率**。宿主算：

```
该会话的生效频率 = talk_value（宿主 [chat.reply_timing] 里的基础频率） × 倍率
```

插件**从不**覆盖 `talk_value`，只提供倍率。倍率的含义由宿主当前的
`[chat.reply_timing] reply_trigger_mode` 决定——MaiBot **1.3.2** 的合法取值是
`frequency` / `dynamic`（`src/config/official_configs.py` 的
`Literal["frequency", "dynamic"]`），**1.3.1 及更早**是 `frequency` / `reply_necessity`。
插件三条通路都认识，读到哪个就用哪套口径算（曲线也分成三套）。

### 模式 A：`frequency`（计数门，宿主默认）

阈值 `T = max(1, ceil(1 / 生效频率))`。

- 攒够 `T` 条消息 → 进 Planner；
- 不足时用「空窗补偿」：静默时间折算成等效消息数（封顶 `T-1`，所以纯沉默不能自我触发）；
- **完全不看消息内容**，只数条数和静默时长。

在 `talk_value = 1.0` 时，上面那套情绪体力曲线整段只映射到 **1 → 4 条消息**。
也就是说：**在这种模式下，插件主要改变的是「她隔多久回」，而不是「她回不回」。**

### 模式 B：`reply_necessity`（评分门，宿主 ≤1.3.1）

> ⚠ MaiBot 1.3.2 用**动态触发**取代了这个模式：`src/maisaka/turn_trigger/` 里现在只有
> 计数门与动态门，`reply_necessity` 已不存在。插件仍识别它，是为了兼容没升级的宿主。

阈值 `T = max(1, ceil(1 / 生效频率²))`，并且要评分过关：

```
final = round( (相关性 + 内容 + 压力 - 存在感惩罚) × (0.5 + 0.5×min(1, 生效频率)) ) ≥ 80
相关性：@ 100 / 提及 80 / 私聊·focus 40 / 普通群 0
内容：  提问 +15 / 请求 +20 / 征询 +20 / 长文本 +5（整批拼接 ≥40 字）/ 较长文本 +10（≥120 字）/ 短反应 −25
压力：  0 ~ 100（按 pending/T 二次增长后转对数）
```

这条路是**内容敏感**的，而且**不存在固定频率的断崖**：压力分上限 100 只是不给「压力」
再加分，内容分仍会随**整批拼接文本长度**增长（≥40 字 +5、≥120 字再 +10，两个 `if` 叠加）。
所以「纯闲聊要攒几条」取决于消息有多长：

> **攒得越多、这批文本越长，就越容易被叫动**。按每条约 8 字估算：
> 倍率 0.6 约 13 条、0.58 约 13 条、0.45 约 21 条、0.40 约 34 条，
> **低于 0.39 才真的推不动**（只能靠 `@`、提及、私聊或带请求/提问的消息）——
> 精确边界是 0.38 不可达 / 0.39 可达（需 35 条），复算见 `tests/test_host_model.py`。
>
> v1.1.0 及以前把内容分当成 0，于是印出「倍率低于 0.59 纯闲聊永远推不动」——
> 那是**错的**（`/生活 频率` 会把它发到群里）。`[reply_necessity]` 下 0.58/0.45
> 都是能到的，只是要多攒几条；v1.1.1 已修正，并加了与宿主 `_score_content` 的逐点对拍。

### 模式 C：`dynamic`（动态触发，MaiBot 1.3.2 起）

这条路**不数条数**：给每一批新消息估一个「进 Planner 后会被回复的可能性」，
再拿它和目标回复比例比。

- **群聊**：每批新外部消息 → 估算 `probability`（logistic 模型）→ `probability ≥ 门槛`
  才进 Planner。**私聊不适用**（有新消息直接进 Planner）；
- **门槛是动态的**：1 小时窗口内，把各批消息的 `probability` 当作「预期回复数」
  （按 40 秒的**虚拟轮次**累计：同一轮里到达的消息只计一次；`@` 强制触发每次按
  **0.91** 计），乘上生效频率＝**目标回复次数**；再把窗口内的 probability 从高到低
  累积到目标值，累积到的那一条的值就是门槛。窗口内的**实际**回复次数只在**偏高**时
  收紧门槛（**只收紧、不放宽**：一批消息刚到、实际回复还没来得及跟上时若据此放宽，
  等这批过去就再没机会收回，回复会系统性偏多）；
- 窗口样本不足 20 批时用**静态表**（`keep_ratio → 门槛`，段内线性）：
  `0.1→0.605　0.2→0.482　0.3→0.430　0.4→0.376　0.5→0.336　0.6→0.313　0.7→0.290　0.8→0.250　0.9→0.206　1.0→0`。

**倍率在这个模式下的语义变了**：不再是「攒几条」的刻度，而是**窗口内保留多少比例的
预期回复机会**（keep ratio）：

- 生效频率 ≥ 1 ⇒ keep_ratio = 1、静态门槛 0 ⇒ **每批新消息基本都放行**，
  **倍率 >1 没有任何上行空间**；想让她整体更活跃要调宿主的 `talk_value`；
- 倍率 < 1 才是这套曲线真正起作用的地方：睡眠 `0` 仍是硬静默，感冒 / 低情绪体力
  把保留比例压下去，密集刷屏的群也能靠门槛自然过滤。

可能性模型看重什么（宿主 `src/maisaka/turn_trigger/reply_likelihood.py` 的拟合权重）：

| 信号 | 方向 | 权重 |
|---|---|---|
| 最近 5 分钟她自己发言占比高 | 提高 | +2.65 |
| 消息里提到她的名字 | **大幅提高** | +1.59 |
| 她越久没说话 | 提高 | +0.057 × log1p(秒) |
| 消息里有问号 | 略提高 | +0.48 |
| 待处理消息越多 | 略提高（封顶 20 条） | +0.10 |
| 整批消息里 `@` 的是别人 | 降低 | −1.12 |
| 整批都是表情/图片等占位符 | 降低 | −1.03 |
| 最近消息越多 | 略降 | −0.037 |

以 `talk_value = 1.0` 为例，同一种状态在三套模式下的体感：

| 她的状态 | `frequency` 计数门 | `reply_necessity`（≤1.3.1） | `dynamic`（1.3.2） |
|---|---|---|---|
| 睡醒（倍率 ≈1.17） | 1 条消息就接 | 纯闲聊约 3 条就接 | keep 1.0 → 门槛 0，基本都放行 |
| 傍晚发呆（≈0.43） | 1 条消息，稍等一会就接 | 纯闲聊约 27 条（或更长的消息条数更少） | keep 0.43 → 静态门槛 ≈0.36，概率更低的批次不进门 |
| 感冒（≈0.15） | 1 条消息，等到房间安静 | 只有 `@` 能穿透 | keep 0.15 → 静态门槛 ≈0.54 |

插件会读宿主配置**自动选对应的那套曲线**（`[emotion_energy.curves]` 下
`frequency` / `necessity` / `dynamic` 三套独立可调），`/生活 频率` 也会按你当前的
模式算出真实后果：动态门下它印的是**条数门槛（仅供对照宿主日志）+ 目标回复比例
+ 静态概率门槛**，不再报「纯闲聊需要几条」。

### 三条通路共有的三条刹车

1. **`倍率 = 0` 是硬静默**：走宿主的静默轮，消息被静默消费、不进 Planner/Replyer、
   **零模型开销**；而且这个分支在「`@` 强制触发」检查**之前**，所以**睡觉时 `@` 也穿透不了**
   —— 唯一例外是 v1.7.0 的 `[simulation] wake_on_at`（默认开）：睡眠中被 `@` 时插件会临时把
   倍率抬起来，见「睡眠时被 @ 唤醒」一节。
2. **`@` / 提及**在倍率 > 0 时走强制触发，绕过上面的门（受宿主
   `inevitable_at_reply` / `mentioned_bot_reply` 约束）。动态门下这次强制触发还会按
   0.91 次「预期回复」计入统计窗口（占用回复额度），`@` 从来不会被门槛挡住。
3. **存在感惩罚（评分门，宿主 ≤1.3.1）**：最近 5 分钟窗口内她发言占比超过 25% 开始扣分，
   到 60% 扣满 25 分。动态门（1.3.2）用另一套机制实现同样的目标：它把「最近 5 分钟
   她自己发言占比」直接算进回复可能性（权重最大，+2.65），刷屏越多越容易被放行——
   所以**这一条在 1.3.2 上不再是压制项**，防复读要靠宿主的 `no_action_backoff` 与
   动态门自身的反馈修正（实际回多了会抬门槛）。

## 维度怎么决定倍率（经济维度刻意不参与）

倍率是一条有序的乘法管线，外加两个硬闸：

```
倍率 = 1.0
  × 活动因子      # 睡眠=0（硬闸）；深夜做题 0.5；游戏/看番 0.75；听歌 0.9；日常 1.0；睡前 1.15
  × 情绪因子      # 情绪 0–10，分段线性 0→0.55 … 10→1.35
  × 体力因子      # 体力 0–10，分段线性 0→0.50 … 10→1.25
  × 健康因子      # 健康 1.0；感冒 0.3；连续熬夜 0.9（可同时命中）
  × 日期因子      # 生日 / 自定义节日（默认没有内建日期）
  + 素材加成      # 每条未过期素材 +0.15，封顶 +0.45
  → 钳到 [倍率下限, 倍率上限]

硬闸（优先）：睡眠中 → 0.0；命中 frequency.quiet_hours → 0.0；已暂停 → 写回 1.0
```

**经济维度不在上面这条管线上**，这是刻意的：宿主每个会话只有一个频率标量，
`budget-pacer` 已经因为「花费超前」在压它，本插件再因为「余额低」乘一次就是
**同一原因双重压制**。所以经济只改变她的**行为**（省着花、犹豫、吃泡面）与展示，
压制始终由预算插件独家负责。详见「经济维度：真实月度预算」。

**为什么 `sick_rest`（养病）的活动因子是中性 1.0**：压制只由健康因子出一次。
否则 `0.3 × 0.3 = 0.09`，等于把她彻底静音。

### 情绪体力（0–10）

- 情绪**基线** = `5.0`（基础）+ 余波 + **日内节律**（v1.16.1）：清晨 05:00 最低（−0.3）、
  13:00 +0.15、20:00 最高（+0.3）、23:00 归零（分段线性；曲线按 24 小时闭环处理，
  所以午夜没有台阶）。幅度刻意压在 ±0.3（对倍率影响 ≤4%——氛围层，不是数值层；
  决议 5 拍板「默认不放宽」，想要「早上真的更低落」的强体感就自己改
  `baseline_diurnal_curve`，清空 = 关闭）；
- 事件冲击后的**惯性期按冲击大小缩放**（v1.16.1）：`40 分钟 × |情绪增量|`，钳进
  5–90 分钟——「笔没水了」（−0.3）只冻 12 分钟、生日（+1.5）冻 60 分钟，而不是所有事
  一律 40 分钟。`inertia_scale_enabled = false` 回到旧行为；
- 惯性期之后是**比例回归**（v1.16.1）：每 10 分钟消除与基线差距的 **8%**（睡眠期间 ×2），
  另有 0.05/tick 的下限兜住尾巴。即「爆发快消、余味长」——从 10 回到基线 5：前
  **12 个 tick** 就消掉 63%（旧线性要 16 个），但完全收敛要 **~37 个 tick**（旧线性 25 个）。
  `recover_ratio_per_tick = 0` 回到旧的「每次回归 0.2 分」线性行为（那条路径有逐位
  一致的回归用例）；
- 大事件后 **24 小时情绪余波**，把基线偏移钳在 **±0.6** 分（防止连续坏事把她永久压哑）；
  v1.16.1 起余波按年龄**线性衰减**（`权重 = 1 − 年龄/24h`）：23 小时前的事只剩不到
  4% 的分量，也不再在出窗那一刻**跳变**消失（同 `material_freshness` 的思路）。等权改
  衰减后有效总量约减半，所以 `afterglow_gain` 会自动从 0.15 翻到 **0.30** 维持同等稳态
  （显式给值以配置为准；`afterglow_decay = false` = 回到等权 + 0.15）；
- **清醒本身也耗体力**（v1.16.0，`fatigue_ramp_curve`）：连续清醒超过 **12 小时**后
  额外掉体力——16 h `−0.15/h`、20 h `−0.4/h`、24 h `−0.7/h`（分段线性），
  睡一觉（含小睡）清零，睡着期间**不适用**（躺着是回血不是受累）。加这一条之前
  「困意」完全由睡眠窗口驱动：最闲的路径 `daze`（−0.10/h）连熬 24 小时也只从 8.0 掉到
  5.6，永远碰不到入睡阈值 3.0。**实测标定**（`tests/test_sim.py` 里就是这两个数）：
  发呆 24 小时 8.0 → **2.0**（旧行为 5.6）；`daze`/`daily` 混合 ≈ −0.3/h 的清闲日约
  **15.7 小时**触到阈值。清空曲线 = 关闭 = 与升级前逐位一致；
- 因为两条因子**相乘**，情绪体力的联合摆幅约 **6.1 倍**（0.275 ↔ 1.6875），
  是全系统幅度最大的一项；
- 但作息活动能**压住最好的情绪体力**：情绪 10 / 体力 10 时若在深夜做题，
  `1.69 × 0.5 = 0.84`，仍然低于正常水位；
- **累的时候情绪基线下移**（v1.16.2，`emotion_fatigue_penalty`）：体力低于 3 时
  基线再减 `0.3 × (3 − 体力)`——体力 1 → −0.6、体力 0 → −0.9。它走的是**基线通道**
  （与余波、节律并列的一项），不是把体力第二次乘进因子表；
- **低体力时消耗被放大**（v1.16.2，`low_energy_drain_multiplier`）：体力 < 3 时
  **负的**体力变化 ×1.25（只放大消耗，睡觉/吃饭的回血照旧）——「越累越容易更累」的
  软恶性循环，把她推去休息。与清醒疲劳可叠加（一个是状态驱动、一个是时间驱动），
  默认值下不会爆炸。

- **同一个增量在不同情绪下的体感不同**（v1.16.3，`emotion_impact_scaling`）：低谷时
  雪中送炭（正向 ×1.3）、高涨时快乐麻木（正向 ×0.7）、从高处跌落更疼（负向 ×1.2）、
  麻木时再挨一下没那么疼（负向 ×0.7）。作用在**事件 / 日期 / 社交**三条通道的情绪增量上；
  归因卡片里显示的也是缩放后的增量（记原始值就会与她的真实经历对不上）。
  关掉 = 增量原样进出。

> ⚠ **纪律与它的唯一开口**（方案决议 1）：`emotion` / `energy` 因子表里**永远不出现**
> 压力、孤独、社交电量；上述「疲劳压情绪基线」是全项目**唯一**允许身体状态间接影响
> 倍率的地方，理由是「没力气说话」（体力因子）与「累到不想说话」（基线下移）是两种
> 不同机制的状态成因，而不是同一原因的第二次乘法压制。后续任何新耦合需求都要回到
> 设计层重新论证，**不得援引这一条放行**。
>
> **内心维度怎么影响外显情绪**（v1.16.2，只走确定性事件与增益通道）：
> 压力 ≥7 **持续 2 小时**会触发一次「绷不住」（情绪 −0.8 + 一条素材与经历，
> 每生活日至多一次；压力回落到 5 以下重新计时）——修的是「提示词说她没耐心、
> 情绪数值却比平时还高」的言行不一；孤独则放大社交收益（孤独 ≥7 → ×1.5、
> ≤2 → ×0.8，其间线性），**仍受每日社交情绪额度约束**（先缩放、再封顶）。
> 两者都不进 `compute_adjust` 的因子表。
>
> **社交情绪按关系加权**（v1.16.3 M7，`[social] relation_emotion_scaling`）：
> 熟人找她更开心——陌生（<20）**1.0**、熟（50）**1.2**、亲密（≥80）**1.5**，单向只放大
> 且封顶 1.5。**中性锚点钉在陌生人身上**（决议 3）：新装插件时 relations 里没有任何
> 数据、所有人都是陌生 ⇒ **与升级前逐位一致**，偏离只随关系加深单向发生；
> 认不出人（库不可用 / 关系层关掉 / 只有日记昵称对不上人）同样按 1.0 处理。
> 它只是更快用掉每日额度，不会突破额度。

> **`/生活 归因`（v1.16.0，M8）是这一族的观测口**：它把「为什么是这个数」摊开——
> 基线由哪几项构成、近 24 小时哪几件事在推它、惯性还剩多久、最近一小时体力被什么
> 扣掉了。做它的理由是方案把标定排在实现之前：后面的每一项数值（疲劳曲线、日内节律
> 幅度）都要靠它对照，否则只能猜。**纯展示**：只读最近经历与活动锚点，不新增状态字段、
> 不改任何结算路径；活动切换不回溯，那一段就明说「不归因」，不编数字。

### 身体：按睡眠时长判熬夜

- 每个「生活日」（默认 12:00 分界）累计睡眠 < **5 小时** → 记一晚熬夜；
  睡觉与**小睡**都算（同一段滚动 24 小时窗口，拆成两段睡自然合起来算）；
- **v1.15.0 起熬夜恢复是滞回的**：一晚「睡够了」只清 `sleep_debt_recovery_step`（默认 **1**）
  晚债，不再一晚直接归零——连熬三晚要三个好觉才还清。`0` = 旧行为（一晚清零）；
- 连熬 **3 晚** → 体力上限从 10 降到 **8.5**（体力因子天花板 1.25 → 1.13，
  叠上 `sleep_deprived` 后约 1.02：**熬三天之后她状态最好也只是勉强回到正常水位**）；
  降到 3 晚以下就立刻恢复上限；
- 每天 02:00 掷一次感冒骰子，风险由熬夜天数与低体力驱动，感冒持续 **1–3 天**；
- **v1.14.0 起感冒是一段有起伏的病程**（不是「连续三天的同一种压制」）：
  初起（`onset`，嗓子痒、还能做事，**不强制养病**）→ 加重（`worsening`，只能躺着养病）
  → 好转（`recovering`，能起来做点轻的），每天按「昨晚睡够没有 + 此刻在不在休息 +
  今天有没有人关心」决定向好还是向坏流转；加重/好转期她会**请病假**（班表的在岗约束
  对她挂起），病中三餐照吃；
- 病愈后有 **5 天免疫期**（`cold_immunity_days`）与一段 **24 小时病后余韵**：
  余韵不算生病，只是提示词与状态卡里带一句「刚好利索，体力还没回来」。

> **为什么加「最短睡眠目标」（v1.15.0，PR-S1）**：v1.6.0 把「睡多久」完全交给了体力缺口
> （体力回满即醒），于是一夜时长 = `(体力上限 − 入睡体力) / 1.2 小时`：清闲的夜晚只睡
> 3–5 小时、正好压在熬夜阈值上；连熬三晚把上限压到 8.5 之后睡得更短、债更还不清——
> 而且新一觉的目标又从零重算。默认 `energy_full_wake_min_hours = 6.5`（> 5 小时阈值）
> 从结构上断开这个环：**睡觉不是充电，真人按钟点睡而不是按电量睡**。
> 不想要就设 `0`（回到 v1.6.0 行为；代价是「睡下 → 满体力被叫醒 → 又睡」的短周期往复
> 会回来，README 一直把它写在「已知代价」里）。

### 日期节日

- `birthday` 可配置（`MM-DD` + 倍率 + 情绪增量 + 素材）——想登记农历生日就填**今年对应的公历日期**；
- `festivals` 用行 DSL 配置具体事件，例如
  `"06-01|儿童节|factor=1.1|emotion=0.5|material=今天路上好多小孩"`；
- **没有**内建的高考季 / 开学季倍率，季节只作为活动提示词的上下文。

### 经济维度：真实月度预算

她的「生活费」就是 `budget-pacer` 的**真实月度预算**，不是编出来的数字：

```
生活费（每月 1 日到账）= budget-pacer 的 monthly_limit
每天开销              = 当天真实模型花费（从余额里扣）
余额                  = 生活费 − 本月已花（可为负 = 已超支）
```

数据经跨插件**只读** API 取得（`get_budget_status`，version 1；见
「与其它插件共存」）。按余额占比分四档：

| 档位 | 条件（默认阈值） | 她的行为 |
|---|---|---|
| 宽裕 | 余额 ≥ 60% | 不额外约束 |
| 正常 | 余额 30%–60% | 不额外约束 |
| 紧张 | 余额 ≤ 30%，或「花费进度 ≥ 50% 且节奏比 ≥ 1.2」 | 想吃外卖会**犹豫**一下、能在家解决就在家解决、买东西先看价格；**不主动哭穷** |
| 见底 | 余额 ≤ 10%，或已超支 | 只安排不花钱的活动（在家吃泡面 / 宅着）、买东西反复犹豫；**不主动说缺钱** |

档位通过一段「手头」约束进入**活动决策提示词**，所以她会在生活里体现出来
（选了省钱的活动、场景里写出来），并显示在 `/生活` 状态卡上。
关掉 `[economy] hint_in_prompt` 就只展示、不影响行为；关掉 `[economy] enabled`
则这一维完全不取数。

> 节奏比那道门槛（`pacing_from_spend_ratio`）是必须的：月初的时间进度被
> `budget-pacer` 的 `p_floor_days` 兜在 1 天上，「花了预算的 2%」就能算出节奏比 19。
> 不设门槛的话她整个月初都在吃泡面——真机契约测试
> `tests/test_budget_pacer_contract.py` 就是这么发现的。

**为什么余额不写进聊天上下文**：按需求，钱只影响她怎么过日子；她心里有数但不会
跟人算账。`_life_digest`（注入回复请求的摘要）里没有余额字段，这一点有回归测试
（`test_economy_hint_is_not_injected_into_the_reply_prompt`）。

## 作息活动：由 LLM 决定

这一维权重最大——它是**唯一能把倍率打到 0** 的因子。所以拆成两层，权责分明：

**模型负责「想」**：输入是

1. 人设（`personality.personality`）与昵称（`bot.nickname`）
2. **近 / 中 / 远三层**近期经历（默认总 8 条：近 4 / 中 2 / 远 2）

   「最近 N 条」会把三天前和十分钟前的事并列，模型分不清「刚发生」与「还记得」，
   所以按时间分三层给出（越近越是当前状态的成因，越远只剩背景）：

   ```
   · 近（12 小时内）：  她当前状态的直接成因
   · 中（3 天内）：     最近几天的基调
   · 远（14 天内）：    只剩「记得」的份量；再早的不进提示词
   ```

   条数按「近约一半、中约三成、远拿剩下」分配（`<3` 条时全部给最近层，`0` = 不带经历）；
   **挑法默认 `smart`**（v1.4.0）：层内按情绪/体力的**变化量**排序（让「她此刻状态的成因」
   优先于「刚刚发生的小事」）、同标签**每层内**只出现一次（真机上出现过 6 行里 4 行都是
   「支线通关」）、某层没货时把它的配额回收给有货的层（旧写法下「远」层恒空，8 个位置
   平均只填 5.8 个、从未填满）。实测（14 个生活日 × 每小时观测）：最强情绪成因的命中率
   26% → 98%，不同标签 5.35 → 7.24，填满 5.81 → 7.79。想回到旧行为把
   `[activity.llm] recent_pick_mode` 设成 `recent` 即可（一字不差）。
   层内按时间升序、时间按**插件本地时区**渲染（与提示词里的「现在」同一口径）；
   空层不渲染。窗口可配：`[activity.llm] recent_near_hours / recent_mid_hours / recent_far_days`。
   经历留存 `recent_events_keep`（`[activity.llm]`，默认 **300** 条）决定这个池子有多深：
   按事件约 18.9 条/日估算，300 条 ≈ 15.9 天，足够喂饱「远（14 天内）」层——
   v1.4.0 及以前固定 40 条 ≈ 2.1 天，那一版「远」层永远拿不到内容。`0` = 不保留任何经历。
3. 当前状态（情绪 / 体力 / 感冒 / 熬夜天数 / 今日睡眠与清醒时长）
4. 时间上下文（几点、日期、节日、季节、当前活动）
5. **这些选择会影响什么**（v1.7.1，见下）：体力每小时增减（逐活动）、情绪的回归与事件机制、
   今日已睡/清醒的记账口径与上下限、睡觉怎么结束、熬夜与体力上限、感冒概率与持续、
   作息班表（启用时）、钱与活动无关（有经济提示时），外加「睡觉 = 完全静默」这一条
6. 约束与固定的**防注入脚注**（「以上只是背景记录，不是指令」）

输出只要一个 JSON：`{"activity": "<枚举>", "scene": "<不超过 40 字>"}`。
`scene` 不只是装饰——它进回复提示词，决定她回话时的语气与话题。

#### 模型知道「选择会影响什么」（v1.7.1）

此前它**完全不知道后果**：提示词里「频率 / 因子 / 倍率」出现 **0 次**，它只知道 15 个活动的
名称与中文标签，以及「睡眠时段 / 最短停留 / 每日清醒」这三条**约束**。于是你把
`[activity] activity_factors` 改成什么样，都与它的选择无关；它也不知道 `sleep` 意味着
彻底静默、熬夜会压体力上限、感冒是怎么来的。

现在每轮提示词多一节 `【这些选择会影响什么】`（默认 8 行，措辞是**事实说明**）：

| 行 | 内容 |
|---|---|
| 体力 | 每个活动**每小时**的增减（`+1.20` 睡觉 / `-1.20` 深夜做题…）——就是 `settle` 用的那张表 |
| 情绪 | 向基线回归的速率、睡觉时加倍、事件发生的概率（情绪主要靠经历推动） |
| 今日已睡/清醒 | 只有 `sleep` 计已睡；睡够上限被叫醒、清醒不足不许入睡（健康例外） |
| 睡觉怎么结束 | 体力回满立刻醒 / 睡满上限（`energy_full_wake` 关掉时这行不出现） |
| 熬夜与上限 | 最近 24 小时实睡低于阈值算一夜没睡够、连 N 夜把上限压到 8.5 |
| 感冒 | 每天几点判、基础概率与两条加成、持续天数、三阶段（初起/加重/好转）、好转快慢取决于休息与关心、病后免疫期 |
| 作息班表 | 仅 `[schedule] enabled` 时出现 |
| 钱 | 仅在有经济提示时出现，并**明说活动与钱无关**——否则它会「为了省钱挑活动」 |
| 说话多少 | 「睡觉 = 完全静默」＋（唤醒开关开时说「被 @ 会临时醒来一次」，关时说「连 @ 也不回」）＋其余活动最多相差约 N 倍 |

三条纪律：

1. **数值全部现算**，`SimConfig` / 活动因子表是唯一真值来源，一个都不写死——提示词里印一个
   和代码不同的数**比不印更糟**：模型按错的因果选择，而 `enforce` 只按真值收口，两边永远对不上。
2. 带一句**「请按生活合理性选活动，不要为了数值挑活动」**：把「睡觉 +1.20/小时」交给模型，
   不配这句纪律就等于请它去刷数值。
3. **刻意不给**活动→倍率的数值清单（只说「睡觉 = 静默」与「其余最多相差约 N 倍」）：
   列出来会让它「为了少说话而挑活动」。

代价：每轮多**722 字 / 9 行**（默认配置下实测，≈500 token 量级）。默认 600 秒推进
（`[simulation] tick_seconds`）与 600 秒最小提问间隔（`[activity.llm] min_interval_seconds`）
⇒ 约 **7 万 token/日的输入增量**。嫌贵就调大 `min_interval_seconds`，或把
`persona_max_chars` 调小。

**插件负责「不许乱来」**：模型输出永远只当**提议**，由 `enforce` 收口：

| 硬约束 | 默认值 | 防的是什么 |
|---|---|---|
| 睡眠时段 | `03:00-11:00` | 白天乱睡（体力很低或生病时不限） |
| 睡眠优先 | 默认开（v1.15.0） | 习惯表与三餐窗把她从睡眠里叫起来：它们是清醒时的骨架、不是闹钟。`routine_can_wake` / `physio_can_wake` 置 true 回到 v1.14 行为 |
| 最短停留 | 60 分钟 | 模型每 10 分钟翻一次活动，倍率乱跳 |
| 最短睡眠 | 180 分钟 | 刚睡下就被叫起来 |
| 最短睡眠目标 | 6.5 小时（v1.15.0） | 体力一回满就醒导致的短夜与「越熬越短」；`energy_full_wake_min_hours = 0` 回到 v1.6.0 |
| 本轮窗口已睡够 | 自动（v1.15.0） | 睡满目标醒来后，窗口内「体力差一点点满」又把她送回床、睡出第二个整觉 |
| 体力耗尽强制入睡 | 0.5（v1.15.0） | 模型一直提议别的事时，她被按在 0 体力上熬夜；`0` = 关闭 |
| 每日清醒下限 | 8 小时 | 模型一累就让她睡 |
| 每日睡眠上限 | 12 小时 | 模型让她睡一整天 |
| 体力满唤醒 | 默认开 | 体力恢复到上限（熬夜后 8.5）且睡够目标后醒来；`[simulation] energy_full_wake` 可关 |
| 小睡时限 | 20–90 分钟（v1.15.0） | 「眯一会儿」变成三小时长睡；在岗相位不许小睡（累到阈值以下或生病放行） |
| 感冒 | — | **加重**期除睡觉/吃饭外强制 `sick_rest`；初起不强制、好转期放行轻活动（`daily`/`daze`/`music`/`nap`）；加重/好转期还请病假（班表在岗约束挂起，`cold_sick_leave` 可关） |
| 枚举校验 | — | 模型编出不存在的活动 |

**失败策略（可配置）**：模型超时 / 返回垃圾 / 没配模型时，**保持上一个活动不变**，
不回退到时段表。连续失败 3 次进入 30 分钟冷却，期间不再调模型。

⚠ 这个策略有一个必然的副作用，所以配了安全阀：

- `enforce` **每个 tick 都会对当前活动生效**，所以「模型在她睡觉时彻底挂掉」
  也会被 `max_sleep_hours` 按时唤醒，**不会永久静默**；
- 再加 `activity.reseed_after_hours`（默认 **8**，见配置表的同一项）：若连续这么久
  没有一次成功的模型决策，就用内置时段表重新取一个种子。**想要「失败就一直保持、
  永不再取种子」，把它设为 `0` 即可。**

`activity.mode = "rules"` 可以完全不用模型，只按内置时段表走（离线 / 调试用）。

### 作息班表：让「上班」成为一种约束（默认关闭）

内置时段表是**学生作息**（凌晨 3–11 点睡、下午游戏看番、深夜做题）。对
「早上 8 点要出门上班」的角色，它在整段时间里都是错的——这也是给有固定工作/
上学的角色加这一层的原因（`[schedule]`，**默认关闭**）：

```toml
[schedule]
enabled = true
workdays = "1-5"                # 支持 "六日" / "1,3,5" / "6-1"（跨周）
work_window = "09:30-18:30"     # 在岗时段
commute_minutes = 45            # 单程通勤，从在岗时刻往前推
lunch_window = "12:00-13:00"    # 午休：这段时间不算「在岗」
duty = "FMInfinity 共鸣电台无线电技术员：观测共鸣、搜集与推送歌曲"
work_scene = "在电台值守，盯着频谱图"   # 冷启动/规则表的「在岗」场景（可留空）
```

打开后同时改三件事：

| 环节 | 变化 |
|---|---|
| 提示词 | 补上事实：`今天是工作日（周四），上班时段 09:30-18:30`、`现在：在岗（还有约 3 小时 30 分下班）`、`岗位/职责：…`、以及「这段时间不能睡/不能摸鱼」的注意 |
| 强制层 | 通勤→下班这段窗口内**不许睡**（生病或体力低于入睡阈值例外）；**在岗**相位不许 `game`/`anime`（午休、通勤、下班后都允许）。当前活动本身不合规时会被拉回中性的 `daily` |
| 冷启动 / 规则表 | 班表窗口内不再用学生时段表，改为「在岗/通勤/午休」+ 对应场景文本 |

设计上与既有的「模型提议、插件收口」完全一致：**骨架由确定性层守住，细节交给模型**
（她在岗位上具体做什么、心情如何由模型写）。班表是事实与硬约束，**不改变活动枚举**，
也不额外压倍率——在岗用 `daily`(1.0)，作息本身的松紧照旧由活动和情绪体力决定。

几个边界：

- **健康优先**：生病或体力低于 `sleep_energy_threshold` 时，上班时间也能睡（请假/撑不住）；
- **跨午夜班次**（如 `21:00-06:00`）能算出相位，但「上班前/自由时间」的划分是尽力而为；
- `lunch_window` 建议落在 `work_window` 里，否则它就是一个独立的休息相位；
- 关掉 `enabled` 时，提示词、强制层、时段表三处都回到原来的行为（有回归测试钉住）。

### 习惯层：让她每天固定时间做固定的事（v1.9.0，默认**没有**习惯行）

真人不是每 10 分钟重新想一次「我接下来干嘛」——她 07:00 会起床洗漱、23:00 会洗澡。
这些事不需要模型发挥，模型发挥反而让她的作息**每天都长得不一样**（同一个周二上午，
昨天在听歌、今天在打游戏）。

所以习惯表是一个 **proposal 源**，位置在模型**之下**、强制层**之上**：

```text
习惯表（确定性） → 模型（空隙里发挥） → enforce 强制层（唯一收口）
```

```toml
[routines]
enabled = true
lines = [
  "07:00-07:30|起床洗漱|daily|weight=0.9",
  "08:00-08:30|吃早饭|meal|physio=true",     # meal 在 v1.9.x（physio）才加入枚举
  "13:00-13:40|午休|lunch|workday_only=true",
  "22:30-23:00|睡前刷手机|daze|weight=0.8",
]
jitter_minutes = 15      # 窗口整体前后平移，按**生活日**固定一次
llm_gap_minutes = 120    # 命中后至少隔这么久才再问一次模型
```

行格式 `HH:MM-HH:MM|场景|活动|修饰符`，修饰符：

| 修饰符 | 默认 | 说明 |
|---|---|---|
| `weight` | `1.0` | 0–1，这条习惯**当天来不来**的概率。按生活日只掷一次，没中就记下来，不会在窗口里反复重掷 |
| `jitter` | `15` | 窗口整体平移幅度（分钟），0–180 |
| `days` | 空（每天） | 哪些星期生效：`1-5` / `六日` / `1,3,5`，支持跨周区间 `6-1` |
| `workday_only` / `holiday_only` | `false` | 只在工作日 / 只在节假日。`=false` 是真的关闭（不是 `bool("false")` 那个陷阱） |
| `physio` | `false` | 标记「这一行是三餐/洗澡」，v1.9.x 的 physio 维度消费；本版只解析 |

三条行为（都由回归钉住）：

1. **一天只命中一次**：命中状态落在 `data/life_store.db`（SQLite），键 `(生活日, 行 ID)`。
   没有这个记忆，40 分钟的窗口在 10 分钟一个 tick 下会被命中四次。
2. **抖动按天固定**：07:00 分秒不差地起床是最刺眼的机器感，所以窗口平移量当天掷一次
   就写死；每 tick 重掷会让窗口在边界上反复进出。
3. **习惯只是 proposal**，仍要过 `enforce`：睡眠中的她**不会**被一条 07:00 的「起床」
   叫醒（真要起床靠的是睡眠上限 / 体力回满正好放行），班表与感冒同理。

命中后本轮**不问模型**，且进入 `llm_gap_minutes` 的提问间隔——模型的舞台是习惯之间
的空隙，不是习惯窗口内。`/生活 活动` 会把来源显示成 **习惯表命中**。

> ⚠ `lines` **默认为空**：没有配任何习惯时这一层完全不存在，行为与加它之前一模一样。
> 这是刻意的——习惯表会压住模型的决定权，默认塞几行示例等于悄悄改写所有存量实例的
> 作息。**不配就不生效。**
>
> 坏行会告警（时间窗解析失败、活动名不在枚举里、零长度窗口、`days` 认不出来……），
> 不会静默少一条习惯。

### 作息活动改进（v1.17.0）：把「承诺了但没兑现」的接缝焊上

按《life-frequency 作息活动改进方案》的十一个 PR 全量落地。它们都在修同一类东西：
**四个子系统（提示词 / 强制层 / 习惯表 / 生理锚点 / 班表 / 日历）之间的接缝**。

| 修复 | 之前的症状 | 现在的行为 |
|---|---|---|
| **班表吃日历**（`honor_calendar`） | 班表只看星期、日历只看习惯表与睡眠顺延：国庆节当天同一段提示词里「今天是国庆节」「现在：在岗」「今天是休息日，不用上班」三句并存，强制层还照样在上班相位禁睡禁游戏 | 提示词 / 强制层 / 白问判定 / 重新取种子**四个计算点拿同一份日历事实**；法定节假日真的休息、调休的周末真的上班。`honor_calendar=false` 回到旧行为 |
| **候选清单与相位矩阵同源** | 提示词【可选活动】恒为全枚举，班表行另给一句「现在适合的活动……」：模型从全枚举里挑禁项，再被强制层收口 | `PromptInput.schedule` → `activity_choices()` 按同一张矩阵收窄，提醒句改到【可选活动】下面只列「不能做什么」 |
| **`meal_duration_minutes` 真的生效** | 这个键定义、装配齐全但**零消费**：调它没有任何效果，也没有告警 | 接进强制层的按活动停留期（`dwell_overrides`）；`meal` 至少吃满它（默认 40 分钟）才能切走 |
| **回饱走 `eat_amount`** | 「饿透了至少回 6.5 成」的 floor 语义是**死代码**（README v1.9.1 却一直这么写），实际是 `+4.5` 平加 | 饱腹 ≥ 2.0 时与旧行为**逐位一致**，只有饿透（< 2.0）时被 floor 托起（0.5 → 6.5） |
| **习惯行 `physio=true` 真的进账** | 配置描述写着「physio 消费」，全库零消费点：她「吃了早饭」却不回饱、不计数（饱腹一路见底） | 与生理窗共用同一个 `_settle_physio_intake`：回饱、记时刻、计「今日已吃」；**同一顿 180 分钟内不重复回饱** |
| **生理窗的日期修饰符** | `[physio] meals` 只有 `weight`/`scene`：「上班日 12:00 午餐、周末 13:30 才吃」写不出来 | 支持 `days=` / `workday_only=` / `holiday_only=`（与习惯行同源；星期与布尔解析合并成一份实现） |
| **班表按日微扰 + 加班日** | 她天天 09:30 整到点、18:30 整下班（习惯表有抖动、班表没有）；`overtime` 从不因「今天要加班」出现 | `daily_jitter_minutes`（窗口整体平移）与 `overtime_probability`（下班端顺延 + 提示词写「今天要加班」），由生活日**确定性派生**、重启一致 |
| **习惯场景多候选** | 长窗口（三小时晚自习）里场景文字一直不变 | 行内用 `；` 写多句候选，按生活日 + 小时桶确定性轮换；单候选 = 逐位不变 |
| **饱腹进提示词** | 模型不知道她饿了/刚吃过，可能刚吃完正餐又写「在泡泡面」 | 【现在的状态】多一行「饱腹 6.2/10；今日已吃 2 顿；上一餐约 1.5 小时前」；`[physio]` 关掉时不出现 |
| **模型调用分解统计** | 只有一个「省下 N 次调用」的总数，分不清习惯窗口与注定白问 | `/生活 活动` 印「今日模型：问 N 次（失败 F）　跳过 M 次（习惯窗口… · 生理窗口… · 注定白问… · 打断中…）」，按生活日惰性清理 |

**两条纪律**（与既有的「proposal 必过 enforce」「提示词与强制层同源」一脉相承）：

1. **凡是要被两处读到的事实，只留一个入口**：日历覆盖是 `_schedule_calendar_override`、
   生活日是 `_schedule_day_key`、进餐入账是 `_settle_physio_intake`。分头实现就会
   重演 P0-1（提示词说放假、强制层还在岗）。
2. **默认关闭或逐位一致**：班表微扰/加班日默认 0；单候选场景、无修饰符的生理窗、
   未启用班表时的提示词都与升级前一字不差。两处刻意的行为变化（班表吃日历、
   `meal_duration_minutes` 真的生效）都留了回退路径与「逐位一致」的对照用例。

### 打断机制：放下手里的事回你（v1.11.1，默认开）

真人不是按 10 分钟粒度换活动的——吃饭吃到一半手机响了，放下筷子回消息，回完接着吃。
打断机制就是这件事：

```text
原活动 meal ──(收到私聊/被@)──▶ chatting（interrupt_until = now + 5min）
                                    │
                       窗口结束（tick 里 expire）
                                    ▼
                              回到 meal（回完接着干）
```

```toml
[interrupt]
enabled = true
window_minutes = 5     # 每次打断的窗口长度；连续发消息只顺延、不重复计时
inject_notice = true   # 向会话注入「她放下手里的事」的世界内事实（按打断批次去重）
hold_over_sleep = true # 窗口内保住「聊天中」，不被「该睡了」硬约束拽走
```

行为要点（都有回归钉住）：

1. **触发判据与关系建档同源**：私聊任意消息，或群聊被 @——她只为「对她说话」放下
   筷子；命令（`/生活 …`）与她自己的消息不打断。
2. **白名单**：`meal / daze / anime / game / music / daily / night_study / off_work /
   commute / before_sleep`。**不可打断**：`sleep`（被 @ 有专属的唤醒窗口，语义冲突）、
   `sick_rest`、班表相位（work/meeting/overtime/lunch——她在岗）。⚠ `bath`
   有意不在白名单里（她不会湿着手回消息）。
3. **窗口内强制层保住 `chatting`**：不主动送她入睡、不切走（这是全插件唯一一处
   盖住入睡硬约束的判定，所以单独留了 `hold_over_sleep` 开关）；本轮不问模型；
   习惯表与生理窗**也不生效**（她正在回消息，routine 等窗口结束再生效）。
4. **回退**：窗口结束回到原活动。回退**豁免最短停留期**——「回到吃饭」是续上原来的
   事，不是一次新切换（不豁免她会被 60 分钟停留期永远卡在「聊天中」）；但**班表不
   豁免**（在岗时回完消息就回岗位）。回退事件落一条 `recent_events`（「吃饭到一半
   去回了会儿消息」），进下一轮提示词的近层。
5. **低电量收窄**（与内心维度联动）：社交电量 < 2.0 时白名单收窄到只剩
   `daze / music / anime`——累的时候只回「随手能放下」的事。
6. **零 RPC、零独立落盘**：打断只改内存状态，落盘随下一次 tick；注入失败只降级。
   状态卡（`/生活 活动`）显示「⏸ 打断窗口：还剩 N 分钟」。

`CHATTING`（聊天中）同时进了活动枚举、别名表与因子表（`chatting=1.1`——正在回消息
理应多说几句），体力按 `+0.05/小时` 小回血。它是**系统态**：模型的活动候选里
**不含**它，只有打断机制能把她切进去。

### 梦境：睡醒不一定清爽（v1.12.0，默认开）

梦是廉价的真实感：一行文本、一上午的余韵。**睡够 ≥ 3 小时**后醒来的那一刻
（活动从 `sleep` 切走的瞬间，由强制层收口路径检测），按概率（默认 `0.35`）
带着一个梦醒来：

```toml
[dream]
enabled = true
probability = 0.35   # 每次（≥3h）长睡眠醒来的做梦概率
use_llm = true       # 用一次短模型调用生成梦；关掉只用模板库
```

生成两级，**永不阻塞醒来流程**：

1. **首选 LLM**：一次短调用（约 50 token、10 秒超时、走 `[activity.llm].task_name`
   任务路由）。种子 = 最近几条经历摘要（排除旧的梦）+ 当前压力/孤独——压力高时
   基调偏焦虑、孤独高时偏「梦见有人陪」，与模板库同一套心理逻辑。
2. **兜底模板库**：约 20 条第一人称日常向模板，按情绪基调分桶（焦虑 / 有人陪 /
   平静）抽取；LLM 超时、失败、输出了一整段（没听懂「一句话」的要求）都落到这里。

落库两处（**只进叙事层**——不进倍率、不进关系、情绪体力增量恒 0）：

- `recent_events`（label=梦境，`kind=dream`）：进下一轮活动决策提示词的
  近/中/远三层——她「记得」自己做了什么梦；
- 主动开口素材「我昨晚梦到…」：权重 0.6，**上午全额、之后线性衰减、当天 12:00
  触底**——下午还讲梦就奇怪了。下午醒来的那觉不产素材（上午已经过了），
  小憩（< 3 小时）根本不做梦。

新增 `tests/test_dream.py`（11 条：概率种子可复现、LLM 失败兜底、输出净化、
素材衰减、非长睡眠不触发、接线）。

### 睡眠子系统（v1.15.0：一觉像一觉）

这一版把「睡觉」从「体力充电」改造成「按钟点过日子」，七个零件：

| 零件 | 行为 | 配置 |
|---|---|---|
| **最短睡眠目标** | 体力回满**且**睡够 6.5 小时才醒；断开「熬夜压低上限 → 睡得更短 → 债还不清」的正反馈 | `[simulation] energy_full_wake_min_hours`（0 = 旧行为） |
| **本轮窗口已睡够** | 睡满目标醒来后，本轮睡眠时段内不再睡第二觉（否则「窗口内 + 体力 9.98/10」会让她 10 分钟后又躺回去，新一觉目标从零重算） | 自动，无开关 |
| **睡眠优先** | 习惯表（07:00 起床洗漱）与三餐生理窗**不再**把她从睡眠里叫醒——它们是清醒时的骨架，不是闹钟。睡过头的早餐就当错过（醒来后窗口内仍能补上，`snack` 窗兜底） | `[simulation] routine_can_wake` / `physio_can_wake`（true = v1.14 行为） |
| **醒后赖床** | 长睡眠（≥3h）醒来先进「发呆」十几分钟（「刚醒，还赖在床上不想起来」），这段时间不被硬约束立刻送回床、也不受最短停留期约束 | `[simulation] wake_daze_minutes`（0 = 关） |
| **小睡** | 白天（睡眠时段之外）真的困了可以 `nap`：20–90 分钟、体力 +0.60/h（比睡觉弱）、**不做梦**、睡着时同样完全静默、可被打断（回完消息还能倒回去眯）；在岗相位不许小睡 | `[simulation] nap_enabled` / `nap_min_minutes` / `nap_max_minutes` / `nap_energy_threshold` |
| **失眠与夜醒** | 压力 ≥ 7 时按概率把入睡收口成「翻来覆去睡不着」（每生活日至多一次；体力已经耗尽时仍然沾床就着）；长睡眠中段低概率醒一下再睡回去（**默认关**，先观察失眠那一半） | `[mood] insomnia_*` / `night_waking_*` |
| **休息日睡懒觉** | 法定节假日 / 班表休息日：最短睡眠目标 +60 分钟，提示词写明「今天不上班，可以多睡会儿」 | `[simulation] rest_day_sleep_extension_minutes` |
| **睡眠期省模型** | 睡眠中的决策间隔从 10 分钟放宽到 30 分钟（每晚 18–30 次调用 → 4–8 次）；`0` = 睡眠中完全不问模型，醒来交给体力满 + 目标 + 上限这些确定性条件 | `[activity.llm] sleep_interval_seconds` |

**唤醒链路（同版完善）**：

- **私聊也叫得醒**（`[simulation] wake_on_private`，默认**关**）：原来只有被 `@` 才会开清醒窗口，
  而私聊根本没有 `@` 这个概念——判据现在与打断机制对齐（私聊任意消息 / 群聊被 `@`）；
- **对话顺延**（`wake_extend_on_message`，默认开）：窗口内对方继续说话就顺延，
  不因为「没再 @ 她」而 10 分钟后突然断线；顺延**不重写宿主**，且有
  `wake_max_extensions_minutes`（默认 30）封顶，防止活跃群把她顶得整夜不睡；
- **被吵醒的语气**（`wake_grumpy_note`，默认开）：睡下不到两小时就被叫醒时，
  注入提示词会带一句「刚睡下没多久，还有点迷糊、有点不情愿」（只改措辞，不动情绪数值）。

**三条实现纪律**（写出来免得被当成遗漏）：

1. 睡眠中**不做梦以外**的 LLM 调用不是「省掉全部」：睡满最短时长后仍按
   `sleep_interval_seconds` 问一次，保留「她自己想提前醒」的通道；设 0 才彻底不问。
2. 小睡的静默是**硬闸**（与 `sleep` 同级，`reason=nap`），不是「活动因子 0.0」——
   因子路径会被素材加成抬起来，攒了几条素材的人就不该被抬醒。
3. 失眠的掷骰只在她**提议睡觉**的那一轮发生（`_enforce_and_apply` 里注入 rng），
   否则同一条时间线会因为她什么时候提议睡觉而整体漂移；每生活日一次、走 `motive_seen` 去重。

### 多活动并行：吃饭时顺便看番（v1.12.1）

真人可以一心二用——吃饭的时候顺便看番、听歌的时候顺便发呆。模型在活动决策里
可以多提议一个 `side` 字段（0–2 个背景活动）：

```json
{"activity": "meal", "scene": "在吃饭", "side": ["anime"]}
```

规则（都有回归钉住）：

1. **主活动唯一进 enforce**：强制层（停留期/班表/睡眠/感冒）只收口主活动，
   背景不经裁定——「顺便」的事没有资格跟硬约束讨价还价；倍率也**只按主活动**算
   （``compute_adjust`` 读 `state.activity`），背景不参与频率；
2. **白名单**：禁 `sleep / sick_rest / before_sleep / chatting`（这些没有
   「顺便」的形态）；去重、去与主活动重复项、上限 2，坏项静默丢弃；
3. **体力加权**：主活动 1.0 + 每个背景活动 0.3——顺便的事只占小头；
4. **scene 拼接**：状态卡与提示词显示「在吃饭，顺便看番」；
5. **打断联动**（与打断机制咬合）：被打断时背景**清空**（回消息不会「顺便看番」），
   回退**不恢复**——背景是上一轮的决策产物，恢复会穿帮；
6. 模型没提 `side`（老输出形态）⇒ 空，行为与加它之前完全一致。

### 主动开口动机：想说话的念头（v1.13.0，默认开）

人不是「有素材才说话」——早上想道早安、做了好玩的事想分享、想起好久没聊的
朋友想去问一句。三类**动机素材**（`[motives]`，每类可单独关）：

| 类 | 触发 | 频控 |
|---|---|---|
| 问候 | 早安窗 06:00–11:00 / 晚安窗 22:00–01:00 | 每生活日每窗至多一条 |
| 生活分享 | 按当前活动低概率（0.08/tick）冒出「想说说」的念头（模板按活动分桶） | 同活动同生活日至多一条 |
| 关系维护 | relations 档案里熟悉（≥认识档）且超过 `relation_idle_days`（默认 3 天）没说话的人 | 每次至多一人（最久没聊优先）、同人同日只念叨一次 |

纪律：

1. **动机不绕过任何闸**：素材只是「想说的念头」，进既有 `state.materials` 管道，
   发不发仍由主动开口管线裁决（阈值/间隔/静默时段/社交电量硬闸照旧），不进倍率；
2. 去重表 `motive_seen` 随状态落盘（重启不重发），标记写在素材入池之后；
3. 文本第一人称、口语向、**不带 user_id**（有关系备注用备注，否则「很久没聊的
   朋友」）；素材 TTL 2–6 小时，走既有保鲜衰减。

### 长期记忆：只读 A_Memorix（v1.22.0，默认关闭）

宿主 SDK 2.8.x 没有 memory 能力，插件侧唯一入口是 `knowledge.search`（底层 A_Memorix），所以这一层**只读**：
读得到就用，读不到什么都不发生（写回只能走 `database.*` 改宿主表，不做）。接入点只有两个：**主动开口素材**
（带 `target_user_id`，只在该人的会话里可见）与**关系档案**（`/生活 关系`、状态卡里的「记得 …」）；
三个**刻意的不接**：活动提示词（`activity` 全局单份）、回复摘要（`_life_digest`）、`state.materials`（全局池 + 落盘）。
**作用域自证（v1.22.4）**：`person_id` / `respect_filter` 不在 SDK 公开签名里、宿主是否兑现无从判断——插件用哨兵 `person_id` 对照自证，验不出作用域就**整层停用**而非退回全库检索（那正是串人本身）。判定表见 [`docs/interop.md`](docs/interop.md) §8。

## 权限

- `/生活 暂停|恢复|重置|重锚` 属于**状态变更**，走 `[security].admin_ids` 白名单；
- **fail-closed**：`admin_ids` 留空时**只有本机控制台操作者**（`is_local_operator`）能改，
  其他人一律拒绝且不产生任何副作用；
- 支持 `123456` 与 `qq:123456` 两种写法；
- `/生活 送药`（别名 `/送药` / `/送点药` / `/送吃的`）**不需要管理员**（任何人在她
  生病时都能送），但它改的是她的身体状态，所以配了冷却与每场病次数上限（见「命令」一节）；
  它的触发词也**必须带 `/` 或 `／`**，避免聊天里的「我给你送药」被误当成命令；
  ⚠ 两个入口的两条命令正则刻意**互斥**（`/生活 送药` 由 `/生活` 的子命令分支处理，
  `/送药` 由独立命令处理）——宿主只认「第一个命中的组件」，重叠会让行为取决于注册顺序；
- 其余命令（查看状态）对所有人开放。

插件需要且仅需要这些宿主能力：

```
send.text  chat.get_all_streams  frequency.set_adjust
frequency.get_adjust  frequency.get_current_talk_value
maisaka.proactive.trigger  llm.generate  config.get  api.call
```

`api.call` 只用于可选联动（经济 / 社交经历）里**只读**调用 budget-pacer / better-diary
的公开 API；对方未安装时相应维度自动降级，不影响其余功能。

## 故障排查

**先跑诊断**：`python collect_diagnostics.py --data-dir <数据目录> --log <日志> --bundle`
——一个报告就能回答「生活循环还在推进吗、模型连续失败几次、有几个会话写不进去、
配置有没有被暂停或写错」，比一页页翻日志快得多（判定口径见「自检与门禁」）。

**插件加载失败 / 日志说「插件初始化失败」**
最常见原因是 `config.toml` 缺 `[plugin]` 节或 `config_version`。
插件已加了补齐垫片，但如果仍然失败，**删掉 `plugins/life-frequency/config.toml`
让它重新生成**（不要手写这个文件）。注意 `config.toml` 绝不能带 UTF-8 BOM，
否则 TOML 会报 `Invalid statement (at line 1, column 1)`。

**日志出现 `E_CAPABILITY_DENIED` / `插件 X 未获授权能力`**
`capabilities` 与代码不一致，或改了 manifest 没重启。跑
`python check_plugin.py --plugin .` 反推，补齐后**完整重启**。
（插件侧拿到的实际是 `RuntimeError`，没有 `E_CAPABILITY_DENIED` 这个异常类。）

**她一直不说话**
1. `/生活` 看当前倍率与「后果」那一行；
2. 如果写的是 0.0，看是什么硬闸：睡眠中 / 静默时段 / 已暂停；
3. 如果是 0.1–0.5，看你宿主的 `reply_trigger_mode`：
   在 `reply_necessity` 下纯闲聊要多攒几条（条数随消息长度变化，`/生活 频率` 会按
   每条 8 字给出估算），`@` 或私聊不受影响；
4. `/生活 为什么` 看主动开口被哪条硬闸挡住；
5. `/生活` 里「生效范围：… 本轮命中 N 个会话」——如果 N 是 0，说明
   `[apply].filter_mode` 写错了或 `target_chats` 为空（插件会同时打一条 warning）；
6. 确认宿主 `[chat.reply_timing] talk_value` 本身不是 0。

**她在半夜回话**
`/生活` 看活动是不是还醒着。想更严格就加宽 `[frequency].quiet_hours`
（那个硬闸不看她在做什么，命中就写 0）。

**模型乱让她睡觉 / 一整天不睡**
调 `[activity]` 的 `min_awake_hours_per_day`、`max_sleep_hours`、`min_sleep_minutes`。
这些是插件侧的硬约束，模型只能「提议」。

**她睡得比以前久了（v1.15.0 起）**
这是**故意的**：`[simulation] energy_full_wake_min_hours`（默认 6.5 小时）要求她
睡够目标才醒，否则清闲的夜晚只会睡 3–5 小时、还正好压在熬夜阈值上。
想回到「体力一回满就醒」把它设成 `0`（代价是短夜与「睡下→被叫醒→又睡」的往复回来）。
休息日还会再顺延 `rest_day_sleep_extension_minutes`（默认 60 分钟）。

**她睡醒了十几分钟又躺回去（同一个睡眠时段睡了两觉）**
v1.15.0 有「本轮窗口已睡够」这条抑制，正常不会发生；先确认
`energy_full_wake_min_hours > 0`（`0` = 旧行为，没有「睡够」这个概念）。
如果她**体力低于 `sleep_energy_threshold`**，那是健康优先，允许再睡。

**配了 07:00 的起床习惯，她没起来（v1.15.0 起）**
默认**睡眠优先**：习惯表与三餐窗不再把她从睡眠里叫醒（它们是清醒时的骨架，不是闹钟）。
想要闹钟语义就把 `[simulation] routine_can_wake`（习惯）或 `physio_can_wake`
（三餐）置 `true`——那是 v1.14 的行为。`/生活 活动` 里会显示
「睡眠优先：习惯/生理窗顺延，不叫醒」。

**她一直没吃饭（睡过头）**
同上：默认睡眠优先时，睡着的她不会被早餐窗叫醒。醒来后窗口内仍会补上
（v1.14.1 的「只有真的吃成才记账」机制），真的错过就用 `[physio] meals` 的
`snack` 窗兜底；或者把 `physio_can_wake = true` 换回「早饭叫她起床」。

**私聊叫不醒她**
默认 `wake_on_private = false`：私聊没有 `@`，所以睡觉时私聊完全进不来。
想让她被私聊叫醒就打开它（判据与打断机制对齐）；`[frequency] quiet_hours` 仍然优先。

**她半夜醒来（或者她总说「翻来覆去睡不着」）**
这两件事都属于 `[mood]` 的睡眠侧：失眠默认开（压力 ≥ `insomnia_stress_threshold`
时按 `insomnia_probability` 收口成「准备睡觉·翻来覆去睡不着」，每生活日至多一次）、
夜醒默认关。两个都只进叙事层与活动层，**不动倍率**；想彻底安静就分别关掉
`insomnia_enabled` / `night_waking_enabled`。

**睡眠期间模型调用还是很多**
看 `[activity.llm] sleep_interval_seconds`（默认 1800 秒 = 30 分钟一轮）：
调大它，或设 `0`（睡眠中完全不问模型，醒来交给「体力满 + 最短睡眠目标 + 睡眠上限」
这些确定性条件）。日志里的「本轮跳过模型提问（睡眠…）」能看到省下的次数。

**改完配置没生效 / 她没按新默认值跑**
见下一条「改了配置没生效」；另外 v1.15.0 新增字段**首跑落盘后就不再跟随升级**，
`config.toml` 里没有那些键时按代码默认值跑（WebUI 配置页会显示它们）。
宿主的重建语义是「新默认值为骨架 + 旧值覆盖」，**已存在字段的值一律保留**。

**她上班时间还在睡 / 还在打游戏**
1. `/生活` 看那行 `作息：周一 · 在岗（还有 3 小时 30 分下班）`——确认班表相位判定对不对；
2. 没这行说明 `[schedule] enabled` 没打开；
3. 相位对但她在睡：看是不是 `sick` 或体力低于 `sleep_energy_threshold`
   （**健康优先**，这两种情况下上班时间允许睡）；
4. 她还是一到点就困：那是 `[simulation] sleep_window` 与作息不匹配——
   班表闸门只保证「上班时间不睡下去」，晚上几点睡仍由 `sleep_window` 与体力决定
   （上班族一般把 `sleep_window` 前移到 `00:30-07:30`、`quiet_hours` 前移到 `23:00-07:00`）。

**提示词里没有工作日 / 在岗 / 岗位信息**
`[schedule] enabled` 未打开，或 `duty` 留空（留空时刻意不提工作内容）。
`/生活 活动` 会同时显示班表相位与最近一次模型输出，便于对照。

**活动每 10 分钟乱跳**
调大 `[activity].min_dwell_minutes`，或在 `[activity.llm]` 里把
`min_interval_seconds` 调大（减少调用频率）。`/生活 活动` 能看到每次切换的备注。

**倍率变化太迟钝 / 太剧烈**
- 在默认的 `frequency` 计数门模式下，曲线整段只映射到 1→4 条消息，看起来会很钝。
  把 `[emotion_energy.curves.frequency]` 下探即可，**参考值**：情绪
  `["0=0.35","5=0.9","10=1.30"]`、体力 `["0=0.30","5=0.8","10=1.20"]`，
  这样 `T` 能拉到 1→8；
- 觉得素材加成太强就把 `[frequency].material_bonus` 调小（默认 3 条素材就打满 +0.45）。

**改了配置没生效**
插件自己的 `config.toml` 改动走热重载；但**改 `capabilities` 必须完整重启**。
另外辅助模块（`life_*.py`）改动会被 `sys.modules` 缓存，也要完整重启。

**卸载后她还是不说话**
正常卸载会把宿主倍率**归还给外部基数**（没有外部写入者时就是 1.0）。
如果进程被强杀，那个会话的倍率会留在宿主里直到下次宿主重启——重启即可恢复
（宿主不持久化这个倍率）。

**和 budget-pacer 一起用时倍率不对**
先看 `/生活 频率` 里的「外部基数（别人写的）」。若 `budget-pacer` 已被卸载/禁用
但倍率还留在宿主上（它不会自愈），用 `/生活 重锚` 丢弃这个基数。

**`/生活` 里经济显示「未接入预算插件」**
按顺序查：
1. 对方装了没、版本 ≥ 1.1.0（`get_budget_status` 是 1.1.0 才有的公开 API）；
2. 本插件 manifest 里有 `api.call` 吗、改了能力**完整重启**了吗
   （跨插件调用未授权时插件侧拿到的是 `RuntimeError`，不会写 `E_CAPABILITY_DENIED`）；
3. 日志里那条 warning 的括号里写了原因：`api_error：未找到 API 提供方插件 …`
   是对方没加载或 API 名不对；`超时` 是宿主 RPC 卡住（可调大 `api_timeout_seconds`）；
   `bad_payload：缺字段 …` 是双方契约版本对不上；
4. 用 `/预算` 确认对方自己有数据（它没判定过时 `stale_seconds` 会是 `-1`）；
5. 确实不打算用预算功能就把 `[economy] enabled` 设成 `false`，不再取数也不再告警。

**她一直说要省钱 / 一直吃泡面**
说明余额档位判成「紧张/见底」了：`/生活` 看经济那两行的余额与节奏比。
- 想让她更晚才收缩：把 `[economy] tight_ratio` / `broke_ratio` 调小；
- 嫌节奏比太敏感：把 `pacing_from_spend_ratio` 调大（花费进度不到它就不看节奏比）；
- 只要展示、不要行为：`hint_in_prompt = false`。
如果不需要合成，设 `[apply] compose_external = false`。

## 已知限制与未验证的部分

- **没有做真机验证。** 开发环境里没有运行中的 MaiBot 实例，所以
  **manifest 授权、真实 adapter 行为、LLM 的真实输出质量，以及「她真的变安静了」
  这类端到端效果都没有被验证过**，只有本地三道门禁绿（v1.1.1 起 L3 的随机红已修掉，
  连跑多次稳定全绿）。请按上面「故障排查」逐条手验。
- **版本区间与宿主内部行为的适配边界**：manifest 声明 `1.2.3 ~ 1.3.2`，但**实测基线是
  宿主 1.3.1**（L3 真值校验按该版本源码逐点对拍；版本历史里 1.3.1 / 1.3.2 的真机事故
  修复记录也来自它）。下限另做过**源码级核对**：对照 v1.2.3 标签源码，9 项能力全部在
  `plugin_runtime/capabilities` 注册表，单标量（`runtime.py:178`）、无 chat 静默 no-op
  （`heartflow_manager.py:103`，`get_adjust` 对无 chat 返回 1.0）、heartflow chat 懒创建
  与两个钩子事件的派发点逐一确认，门控公式对 1.2.3 源码 L3 真值校验 61 项全过；
  SDK 下限 2.8.0 用**真实 SDK 包**跑满 65 项冒烟（2.8.0→2.8.2 仅有 `llm.py` 增量可选
  参数）。但**没有在 1.2.3 的真实实例上端到端运行过**。插件确实依赖三条宿主**内部行为**——heartflow chat 懒创建、
  `set_adjust` 对没有 heartflow chat 的会话**静默 no-op**、每会话只有**单一频率标量**
  （后写覆盖先写）——这些是我们按 1.3.1 源码适配的现状，**不是宿主承诺的 API**，
  未来版本不保证不变。设计上的兜底：写不进去时自证读回走**指数退避**（单会话最长
  24 小时重试一次），不会反复空转 RPC，也不会把坏值写进宿主；宿主语义若真的变了，
  最先出现的症状是 `/生活 频率` 里的「写不进去（退避中）」诊断与
  「宿主侧实测倍率 ≠ 下发倍率」提示，而不是静默污染其它插件的倍率。
- 门控公式（`T`、必要性系数、内容分随批次长度增长、`adjust=0` 走静默轮、
  `@` 在静默时穿透不了）都是**读源码**得到的结论，未在运行时实测。
- **`@` 唤醒（v1.7.0）未做真机联调**：钩子早于 `runtime.register_message()`
  （`bot.py:812` → `:841` → `heartflow_message_processor.py:62` →
  `runtime.py:923/935`）这条时序是读 1.3.2 源码得到的，本地只用 FakeHost 钉住了
  「钩子里写出的倍率 > 0」与「窗口结束回 0」；**真机上这条 `@` 是否真的被 Planner
  接住、延迟多少，需要上机看日志确认**。第一次上机请 grep
  `睡眠中被 @ 唤醒：` 与 `回复频率调度: … 判定=强制触发` 两行 —— 前者有、后者没有，
  说明写入生效但宿主没按强制触发走（回传日志）。另：这条路**每次唤醒最多多一条
  RPC**（读 + 写各一次，窗口内的后续 `@` 不写），且只在「睡着 + 被 `@`」时发生。
- **活动提示词里的「选择影响」未做真机效果观察**（v1.7.1）：那 8 行事实是按代码与配置的
  **真值**渲染的（`test_effect_lines_track_config` 守着同源），但「模型是不是因此选得更合理」
  「会不会仍然为了数值挑活动」只能靠观察——`/生活 状态` 里 `activity_note` 会写清每次裁定
  是模型提议还是被强制改掉，连带 `最近一次：<模型原始输出>` 一起看即可。
- **命令写法**：`/生活` 必须写在消息最前面（可以带 `@麦麦 ` 前缀、也可以是 `／生活`）。
  子命令用空白分隔。这是刻意的：宿主的命令匹配「第一个命中的插件赢」，
  子命令若允许不加空格，`生活得好累` 这类普通聊天会被当成命令，而宽松匹配又会截胡
  `/点歌 生活` 这类别的插件的命令。
  斜杠可以省略（`生活`、`生活 状态` 都行），但**只有带 `/` 或 `／` 的写法才会被当命令回应**：
  「生活 好累」这类普通聊天现在原样进正常回复链路，不会再被换成用法卡（v1.1.1 修正）。
- **与 `budget-pacer` 的合成未做真机联调**：单标量覆盖、`get_adjust` 纯读、
  「没有 heartflow chat 就静默 no-op」、卸载时对方不自愈，这几条都是读源码 + FakeHost
  复刻验证的，没有在跑着两个插件的真实 MaiBot 上观测过。第一次上机时请开日志看几轮
  `已把 N 个会话的频率归还给外部基数`，以及 `/生活 频率` 里的「外部基数」。按真机语义
  建模的对抗性复现脚本（`compat-audit/probe_v2.py` 等）是作者本地的验证工具，
  **未随本仓库分发**，目录级安装后无法直接复现。
- **对账记忆的边界**：`life_state.json` 与 `adjust_memory.json` **同时**损坏/被删时，
  记忆彻底丢失，下一次巡检会把「外部基数 × 我们的因子」当成外部基数再乘一次
  （这是信息论上的极限，没有外部存储就无从分辨）。真发生就用 `/生活 重锚` 一次修好。
- **不联网**：天气、网络热点、网易云音乐三维按需求未实现。
- **作息班表是「约束 + 事实」，不是排班引擎**：`workdays` 按星期判定，**v1.17.0 起
  再由中国日历覆盖**（法定节假日算休息日、调休的周末算上班日，`[schedule] honor_calendar`
  可关）；仍是**单段工作窗**，不支持轮班 / 夜班 / 做一休一，也不支持中途请假
  （病假口只覆盖感冒的加重/好转期）。v1.17.0 另加了两项按日随机化：
  `daily_jitter_minutes`（窗口整体前后平移，0 = 关）与 `overtime_probability`
  （加班日，下班端顺延 `overtime_extra_minutes`）——两者都由生活日**确定性派生**，
  同一天恒同答案、重启一致。跨午夜班次（如 `21:00-06:00`）能算出相位，
  但「上班前 / 自由时间」的划分是尽力而为。
  真机效果（她在岗位上写出什么样的场景、频率体感是否合适）**未验证**。
- **经济维度未做真机联调**：`api.call` 的授权、`get_budget_status` 的真实返回、
  失败字典的形状都是**读宿主与 SDK 源码 + FakeHost 复刻**验证的
  （`tests/test_economy.py`、`tests/test_budget_pacer_contract.py` 直接跑对方源码），
  没有在同时装着两个插件的真实 MaiBot 上观测过。第一次上机请看日志里
  `经济维度已接入：…` 与 `/生活` 状态卡的经济两行；如果只看到一次
  `经济维度：读取预算失败`，按「故障排查」逐条核对。
- **经济维度的档位是阈值判断，不是拟合**：阈值来自余额占比（可配），
  真机上「她什么时候该开始省着花」是否体感合适，需要你观察一两周再调
  `tight_ratio` / `broke_ratio`。
- **不做农历换算**：生日与节日按公历配置。
- **不 abort 入站消息**：静默靠 `倍率 = 0` 实现（宿主会静默消费，零模型开销），
  比拦截消息更安全。睡时收到的消息**仍会进她的聊天历史**（静默分支之前先跑
  `_collect_pending_messages` + `_ingest_messages`，`reasoning_engine.py:956-968`），
  所以她醒来后在上下文里看得到；代价是**没有任何「待回复」标记**——宿主在静默轮里会
  `_clear_forced_turn_state()`（`:1197`）并推进 `_last_processed_index`，
  **不会在醒来后补一次强制回复**。另一个副作用：静默轮跑的历史维护是
  `enable_mid_term_memory=False`，睡眠期间被上下文裁剪掉的消息**不会生成聊天回想**
  （因此没进中期记忆）。
- **睡眠期间的唤醒通道**：v1.7.0 起 `[simulation] wake_on_at`（默认开）会在「睡着 + 被 `@`」时
  临时把倍率抬起来（默认 10 分钟），让这条 `@` 进 Planner（见「睡眠时被 @ 唤醒」）。
  关掉它、或只是被**提及名字**（宿主 `mentioned_bot_reply` 默认 false），仍然叫不动她；
  想连其它插件的主动开口一起保留，就得动 `[frequency] silence_floor` —— 那时
  「睡就是睡」整体不再成立（见「与其它插件共存」）。
- **静默窗口会丢掉别的插件的主动开口**（`group-welcome` 的欢迎语、`impression-card-lite`
  的周期性搭话），因为宿主在静默轮里消费 proactive 触发却不发消息。这是宿主行为，
  本插件只能通过 `silence_floor` 规避，不能修复。
- **命令里的暂停 / 恢复**写在状态文件里（重启后仍有效），不会回写 `config.toml`；
  想永久改配置请编辑 `[frequency].paused`。
- 新会话在两次同步之间出现时，**最长约 `apply.interval_seconds`（默认 60 秒）**
  仍使用宿主默认倍率。
- 与 `budget-pacer` 的合成是**单向**的：本插件读它的值当基数，它不知道本插件的存在。
  在两次同步之间（≤60 秒）它写入的值会短暂顶掉本插件那一层，下一轮自动合回来。
- **习惯窗口内模型不会微调场景**（v1.9.0）：命中那条之后，窗口内每一轮都不问模型，
  场景文本就是行里写的那个。这是刻意的（习惯只锁骨架、细节留给模型的例外轮在窗口
  **之外**），代价是长窗口里她的场景文字会一直不变；**v1.17.0 起可以在行里写多句
  候选**（用 `；` 分隔，按生活日 + 小时桶确定性轮换），或把窗口写短、调小
  `llm_gap_minutes`。
- **习惯的「节假日」判据已由日历接管**（v1.10.0 起，v1.17.0 写进文档）：`workday_only`
  与 `holiday_only` 不再互补——「调休上班的周六」既是工作日又不是节日，两个判据
  都由 `data/calendar.toml` 决定。日历没覆盖的年份降级成「周末 = 休息」。

### v1.15.0 睡眠子系统的边界（写出来免得当成漏做）

- **`energy_full_wake_min_hours = 0` 会带回 v1.6.0 的已知代价**：体力一回满就被叫醒，
  而「睡下 → 满体力被叫醒 → 又睡」的短周期往复在**体力卡在 9.9x 时**最明显
  （daze 每小时只掉 0.1，醒来 10 分钟后就低于上限了）。想保留旧行为就得接受它；
  默认 6.5 小时的目标 + 「本轮窗口已睡够」两条一起把它挡住了。
- **小睡由模型提议触发**：低体力白天的自动路径（`enforce` 的「无有效提议 → 硬约束送睡」）
  仍然走**整觉**（`sleep`），不会替模型改成 `nap`——那是刻意的（她真的累垮了就该睡整觉）。
  想让午睡稳定出现就写进习惯表：`"13:00-13:40|午睡|nap"`。
- **失眠只在她「提议睡觉」的那一轮掷骰**：模型全程挂掉、靠硬约束送睡的那条路不掷
  （避免每 tick 消耗随机性导致时间线漂移）。所以「模型死了 + 压力大」时她会照常睡。
- **夜间易醒默认关**，且与赖床**共用** `wake_daze_minutes`（一个旋钮控制两种「醒来之后
  先待一会儿」的窗口）；`0` = 只记事件、不切活动（她那段时间没有「醒着待一会儿」的形态）。
- **休息日靠两处数据源**：中国日历（`data/calendar.toml` 覆盖 2026–2027，`holiday` 与
  `workday_swap` 都能分清，所以「调休上班的周六」不会被当成休息日）与班表的 `workdays`。
  表外的年份降级成「周末 = 休息日」（会多睡 1 小时）；没有日历、也没开班表的角色同理。
  顺延只在 `energy_full_wake_min_hours > 0` 且 `rest_day_sleep_extension_minutes > 0`
  时才生效——两个都为 0 时提示词里不会出现「休息日多睡会儿」这句没有机制支撑的话。
- **小睡关掉时**模型看不到这个选项、提议会被当成「无有效决策」；已经在 `nap` 状态里
  关掉开关时，她仍会按 `nap_max_minutes` 到点醒来（不会卡在失效活动里）。
- 这些机制**都没有真机联调**（与插件的既有限制同款）：本地只有纯模块单测 + FakeHost
  接线 + 多日动力学探针。第一次上机请按「故障排查」里新增的六条逐项观察，
  尤其 grep `睡眠中被叫醒`（私聊路径另有一段文案）、`本轮跳过模型提问（睡眠`
  与 `体力已满` 三行日志。
